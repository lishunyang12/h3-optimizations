# Run the PRO 5000 reference workloads on PRO 5500

[PRO 5000 data](../benchmark/SM120/README.md) ·
[Docker setup](SM120_DOCKER.md) · [Manual target launcher](../scripts/run_pro5500.sh) ·
[Manual setup](CROSS_SKU_REPRO.md) · [Validation and provenance](VERIFIED_CONTEXT.md)

This handoff runs exactly two workloads: the deployed 5s avatar and the 15s
FastH3 reference. The target is the machine referred to as "PRO 5500" by the
requester. Its exact GPU identity and results remain unverified. The launcher
checks the hardware it actually finds; its name does not certify device support.

**Using the prebuilt Docker image? Follow [Docker image](#docker-image-recommended)
below. You do not need the manual Prepare or Preview and run sections.**
The image already contains the dependencies and both prepared runtimes; its
entry point generates the machine-path configuration inside the container.

## Requirements

Use 8 idle GPUs of the same SKU with SM120 support, the recorded BF16 RDMA path,
and the pinned software environment. The conservative total-VRAM guards are
60000 MiB for the avatar and 65147 MiB for FastH3. The avatar also requires at
least 400 GiB of available host RAM for its retained BF16 weights. These are
package guards, not measured minimum capacities. A target that fails these
requirements needs a separately qualified configuration, not an apples-to-apples
result from a silently changed workload.

Docker still requires a compatible host driver, NVIDIA Container Toolkit and the
recorded RDMA path; no-NIC execution is not supported by these profiles.

### Load the image

If `h3-sm120:20261027` is already loaded, continue to model preparation. Otherwise,
use the [download-and-load instructions](SM120_DOCKER.md#get-the-prebuilt-image).
Building another image from source is optional. Use the identical image on both
the reference and target machines.

### Prepare external model assets once

If you already copied the complete prepared `h3-models` directory from the
reference machine, skip both commands below and reuse those exact sidecars.
Otherwise, create it and download the pinned weights:

```bash
mkdir -p "$PWD/h3-models" "$PWD/h3-results"
docker run --rm \
  --mount type=bind,src="$PWD/h3-models",dst=/models \
  h3-sm120:20261027 download
```

Build both AdaLN sidecars once on an idle GPU; this is outside benchmark timing:

```bash
docker run --rm --gpus '"device=0"' --ipc=host \
  --mount type=bind,src="$PWD/h3-models",dst=/models \
  h3-sm120:20261027 caches
```

The model downloader writes `model-assets.json` for each workload. Keep the whole
directory mounted at `/models`; its model views contain absolute symlinks inside
that mount. Copy the complete directory, including both sidecars, to the other
machine instead of independently regenerating caches. Do not repeat `download`
or `caches` over existing outputs; they deliberately refuse to overwrite them.

### Preview and run in Docker

After the model directories are prepared, preview both launch commands without
GPU access:

```bash
docker run --rm \
  --mount type=bind,src="$PWD/h3-models",dst=/models,readonly \
  h3-sm120:20261027 run \
  --gpus 0,1,2,3,4,5,6,7 --output /results/pro5500-plan --dry-run
```

Run both workloads sequentially on eight idle GPUs:

```bash
mkdir -p "$PWD/h3-results"
docker run --rm --gpus all --pid=host --ipc=host --network=host \
  --device=/dev/infiniband --ulimit memlock=-1 --cap-add IPC_LOCK --cap-add SYS_NICE \
  --mount type=bind,src="$PWD/h3-models",dst=/models,readonly \
  --mount type=bind,src="$PWD/h3-results",dst=/results \
  h3-sm120:20261027 run \
  --gpus 0,1,2,3,4,5,6,7 --output /results/pro5500
```

Results appear under `./h3-results/pro5500` on the host. Use a new output directory
for every run. The image's `run` command starts the same shared benchmark suite as
the manual shell launcher, including warmup, media validation and GPU ownership
checks. `SYS_NICE` is required by the recorded 15s NUMA policy; see the
[Docker guide](SM120_DOCKER.md#run-and-compare).

The dry-run checks command construction, not GPU correctness or target memory
fit. Fresh video inference with the packaged launcher remains pending.

## Manual setup (alternative)

This section is for running directly in a prepared host Python environment.
Docker users can continue to [Results](#results).

### Prepare

```bash
git clone https://github.com/lishunyang12/h3-optimizations.git
cd h3-optimizations
git rev-parse HEAD  # Use this same revision on both machines.

python3 scripts/export_pro5000_reference.py --check
python3 scripts/sku_benchmark.py prepare --variant avatar5 --output /opt/h3-runtime-avatar5
python3 scripts/sku_benchmark.py prepare --variant reference --output /opt/h3-runtime-15s
cp configs/sku-assets.example.json /tmp/h3-assets.json
```

Use new, writable runtime directories. Follow the [full setup guide](CROSS_SKU_REPRO.md)
to install the pinned dependencies, obtain model weights and generate the two
AdaLN sidecars. Copy the same sidecar bytes to both machines. Edit the `runtime`,
`python`, `model`, `adapter`, `adaln` and `cuda` paths in each asset entry. Keep the
case files, prompts, seeds, precision, frame counts and overlap unchanged.

### Preview and run

From the repository root, preview both launch commands without GPU access:

```bash
bash scripts/run_pro5500.sh \
  --assets /tmp/h3-assets.json --gpus 0,1,2,3,4,5,6,7 \
  --output /results/pro5500-plan --dry-run
```

After preparation, run both cases sequentially:

```bash
bash scripts/run_pro5500.sh \
  --assets /tmp/h3-assets.json --gpus 0,1,2,3,4,5,6,7 \
  --output /results/pro5500
```

Each case starts its own local server, performs its fixed warmup sequence,
measures the formal requests, checks the outputs and closes its server.
The script delegates to `sku_benchmark.py suite --cases main`, so the reference
and target use identical timing and validation code. It records the actual GPU
name, PCI IDs, architecture and memory. It rejects occupied GPUs and cleans up
only its own service process group. Use `--port PORT` if the default is occupied.

No target GPU run has been performed as part of this publication. The dry-run
checks command construction; it does not establish memory fit or performance.

```text
/results/pro5500/

  5s-avatar-ref2va-4step/
    result.json                 Timing samples and hardware/software identity
    assets.json                 Actual model, adapter, reference and cache hashes
    sources.json                Actual source and binary fingerprints
    environment.json            Resolved launch environment
    server.log                  Execution and dispatch records
    telemetry.jsonl             Sampled GPU memory, clocks and power limit
    00-warmup.mp4 ...            Warmup and measured outputs
  15s-4step-mxfp8-sage-nvfp4/
    result.json ...              Same artifact layout
```

The new timer spans local curl launch through the complete MP4 written to disk.
Media probing, full audiovisual decoding and hashing occur outside the timer.
Warmup is excluded from the formal statistics. The avatar replay excludes the
application-ready checks measured separately in the historical run.

## Compare against a fresh PRO 5000 run

Run the same workload on the reference system with `--output /results/pro5000`.
For Docker, reuse the same image and prepared model directory on both systems.
Copy both result directories onto one machine, then choose the matching method.

### Docker comparison

With both runs under the host's `./h3-results` directory:

```bash
for h3_case in 5s-avatar-ref2va-4step 15s-4step-mxfp8-sage-nvfp4; do
  docker run --rm \
    --mount type=bind,src="$PWD/h3-results",dst=/results \
    h3-sm120:20261027 exec python3 scripts/sku_benchmark.py compare \
    "/results/pro5000/$h3_case/result.json" \
    "/results/pro5500/$h3_case/result.json" \
    --output "/results/$h3_case-comparison.json"
done
```

### Manual comparison

With the results available at `/results` in the host Python environment:

```bash
python3 scripts/sku_benchmark.py compare \
  /results/pro5000/5s-avatar-ref2va-4step/result.json \
  /results/pro5500/5s-avatar-ref2va-4step/result.json \
  --output /results/avatar-comparison.json

python3 scripts/sku_benchmark.py compare \
  /results/pro5000/15s-4step-mxfp8-sage-nvfp4/result.json \
  /results/pro5500/15s-4step-mxfp8-sage-nvfp4/result.json \
  --output /results/fasth3-comparison.json
```

The comparator requires successful, uncontaminated runs with matching cases,
sources, dependencies and model/cache hashes. It reports each median, the
reference/target latency ratio, host differences and output-byte equality.
Historical PRO 5000 numbers remain useful reference data, but their original
client timing code differs: they are not a substitute for this fresh comparison.
CPU, driver, power and interconnect differences remain part of system latency.
